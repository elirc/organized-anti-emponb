# Schemas, Transactions, and the N+1 Trap: Database Layers

The database is the ultimate source of truth. A junior engineer who treats database transactions loosely, ignores index keys, or writes loops that execute individual database queries will cause application latency to spike and invite data corruption.

---

## Prisma Schema Configurations and Index Mapping

We utilize Prisma ORM to interact with our SQLite database. Look at our OnboardingCase schema representation:
[backend/prisma/schema.prisma:18-24](backend/prisma/schema.prisma#L18-L24):

```prisma
model OnboardingCase {
  id                 String           @id @default(uuid())
  status             String           // DRAFT, NOT_STARTED, IN_PROGRESS, BLOCKED, PENDING_APPROVAL, COMPLETED, CANCELLED
  progressPercent    Int              @default(0)
  startDate          DateTime
  completedAt        DateTime?
```

Every database table should have declared **Index Mappings** on fields used in `WHERE`, `ORDER BY`, or `JOIN` statements. Without indices, the database engine must execute a full table scan, reading every row from disk sequentially to locate records.

## Interactive Transactions and Isolation Levels

When updating multiple tables (e.g. generating concrete tasks, updating status, and writing audit logs during workflow launch), performing these updates outside a transaction is high-risk. If a middle query fails, the database is left in a half-written, corrupt state.

We prevent this by wrapping critical updates in a **Prisma Interactive Transaction**:

### Why Transactions are Mandatory:
1. **Atomicity (All-or-Nothing)**: If an exception is thrown inside the callback (e.g., resolving assignees fails), all updates made during the block are rolled back instantly.
2. **Consistency**: The `tx` argument passes a scoped database client reference. All database actions must use this `tx` reference to execute within the transactional boundary.

## The Fatal N+1 Query Trap

The N+1 trap is one of the most common performance bugs in ORM-driven codebases. It occurs when you fetch a list of parent records, loop over them, and execute a separate database query for each child record:

```ts
// Illustrative — not from the repo (The N+1 Trap!)
const cases = await prisma.onboardingCase.findMany();
for (const c of cases) {
  // FATAL: If you have 100 cases, this executes 100 separate database queries!
  const tasks = await prisma.onboardingTask.findMany({ where: { onboardingCaseId: c.id } });
}
```

To prevent the N+1 trap in our production modules, we systematically leverage **Eager Loading Relations** directly in the database lookup query. Inspect how this is accomplished:
[backend/src/modules/onboardingCases/onboardingCases.service.ts:65-71](backend/src/modules/onboardingCases/onboardingCases.service.ts#L65-L71):

```typescript
    return prisma.onboardingCase.findMany({
      where,
      orderBy: { startDate: 'asc' },
      include: {
        employeeProfile: true,
        department: { select: { id: true, name: true } },
```

By including the `employeeProfile` and `department` tables inside the `include` parameters, Prisma performs a single optimized query with JOIN statements. All related child records are fetched and mapped in a single database roundtrip!

> **Senior aside:** *Always inspect server logs in local environments to confirm the exact SQL statements generated by the ORM. If a single page dashboard triggers dozens of SQL logs, you have written an N+1 trap.*

## Pitfall Checklist

1. **The N+1 Query Loop**: Iterating over database rows and executing separate SQL lookups inside loops.
2. **Missing Transactional Scope (`tx`)**: Forgetting to pass the interactive transaction client reference `tx` inside a transaction block, executing queries on the main connection pool instead.
3. **No Index on Foreign Keys**: Declaring relations in Prisma without mapping indexes, forcing full table scans on joins.
4. **Incorrect Transaction Scope**: Placing network requests or third-party API dispatches inside a database transaction block, exhausting connection pool sizes.
5. **SQLite Isolation Level Collisions**: Executing heavy write operations concurrently on SQLite, causing database lock errors.
6. **Querying Un-needed Fields**: Fetching large text and binary fields when only ID keys are required. Use `select` filters instead.
7. **No Transaction Rolled-back Catching**: Expecting transaction rollbacks to happen automatically without throwing errors out of the interactive scope.
8. **Implicit Type Casting in Queries**: Querying columns using incorrect types (e.g. numeric variables on uuid fields), triggering database compilation faults.
